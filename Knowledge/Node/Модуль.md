> ізольована одиниця коду, який інкапсюлює свою реалізацію, має власну область видимості (scope) і взаємодіє з іншими модулями через явно визначений публічний інтерфейс.

Простіше кажучи: модуль — це файл (або група файлів), який:
- Робить одну конкретну річ (або набір пов'язаних речей)
- Ховає свою внутрішню реалізацію від зовнішнього світу
- Надає публічний API — те, що інші можуть використовувати

### Аналогія

Уяви кухонну техніку. Блендер — це "модуль":
- Ти знаєш його інтерфейс: кнопка "вкл", вибір швидкості, отвір для продуктів
- Ти не знаєш (і не мусиш знати), як всередині обертається мотор
- Якщо блендер зламається — ти замінюєш його, не перебудовуючи всю кухню

Так само працює модуль у коді.

## Навіщо потрібні модулі

### Проблема без модулів

Уяви один файл `app.js` на 10 000 рядків:

```js
// app.js — все в одному файлі
var userName = 'John';
var cartItems = [];
var dbConnection = null;

function validateEmail(email) { /* ... */ }
function connectToDb() { /* ... */ }
function addToCart(item) { /* ... */ }
function renderPage() { /* ... */ }
function sendNotification() { /* ... */ }
// ... ще 500 функцій
```

Проблеми:
1. **Неможливо орієнтуватися** — де шукати потрібну функцію?
2. **Конфлікти імен** — хтось вже використав назву `data`? `result`? `temp`?
3. **Все залежить від всього** — зміна в одному місці ламає інше
4. **Неможливо працювати в команді** — merge conflicts на кожному кроці
5. **Неможливо перевикористовувати** — хочеш `validateEmail` в іншому проєкті? Копі-пасти весь файл?

### Що дають модулі

| Принцип | Що це означає |
|---|---|
| **Інкапсуляція** | Внутрішні деталі сховані. Зовнішній код бачить тільки публічний API |
| **Separation of Concerns** | Кожен модуль відповідає за одну область: валідація, БД, рендеринг |
| **Перевикористання** | Модуль `validateEmail` можна підключити в будь-який проєкт |
| **Namespace** | Змінні модуля не потрапляють у глобальний scope |
| **Тестування** | Можна тестувати модуль ізольовано від решти системи |
| **Командна робота** | Різні люди працюють над різними модулями без конфліктів |
| **Підтримка** | Баг у валідації? Іди в `validation.js`, а не шукай по 10 000 рядків |

## Навіщо потрібна система модулів

Модуль — це концепція. А **система модулів** — це конкретний механізм, який дозволяє:

1. **Визначати модуль** — оголосити, що цей файл є модулем з певним API
2. **Експортувати** — вказати, що саме модуль надає назовні
3. **Імпортувати** — підключити те, що потрібно з іншого модуля
4. **Ізолювати** — гарантувати, що внутрішні змінні не витікають
5. **Розрішувати залежності** — знайти модуль за його іменем чи шляхом

### Чому не можна просто "розбити на файли"?

В ранньому JavaScript (до модульних систем) ти міг розбити код на файли:

```html
<script src="utils.js"></script>
<script src="validation.js"></script>
<script src="app.js"></script>
```

Але це **не модулі**, бо:
- Всі змінні потрапляють у глобальний `window`
- Порядок `<script>` критичний — переплутай і все зламається
- Немає явних залежностей — непонятно, що від чого залежить
- Конфлікт імен між файлами — `utils.js` і `validation.js` обидва оголосили `function format()`?

Система модулів вирішує ці проблеми, надаючи **формальні правила** для організації та зв'язування коду.

## Еволюція модульних систем у JavaScript

```
Глобальні скрипти (до 2009)
    ↓
Паттерни: IIFE, Revealing Module (костилі)
    ↓
CommonJS (2009) — для Node.js, синхронний
    ↓
AMD / RequireJS (2011) — для браузера, асинхронний
    ↓
UMD — спроба об'єднати CJS + AMD
    ↓
ECMAScript Modules (2015+) — офіційний стандарт мови
```

### IIFE — модулі до модульних систем

До CommonJS розробники імітували модулі через Immediately Invoked Function Expression:

```js
var MyModule = (function() {
    // приватні змінні — не видно зовні
    var secret = 42;
    
    // публічний API
    return {
        getSecret: function() { return secret; }
    };
})();

MyModule.getSecret(); // 42
// secret — недоступний зовні
```

Це працювало, але було костильним рішенням без стандартизації.

## Ознаки гарного модуля

1. **Робить одну річ** — Single Responsibility Principle
2. **Мінімальний публічний API** — експортуй тільки те, що потрібно
3. **Не має побічних ефектів при імпорті** (в ідеалі) — імпорт не повинен запускати логіку
4. **Явні залежності** — все, що потрібно, імпортується на початку
5. **Самодостатній** — можна зрозуміти модуль, не читаючи всю кодову базу
