Це модель [[Cloud Computing]], де ти отримуєш готову платформу для розробки й запуску застосунків: рантайм, ОС, часто БД і деплой — без керування серверами вручну.

Як приклад: оренда мебльованої квартири з кухнею — ти не будуєш стіни й не проводиш воду, просто живеш і готуєш. Food court у торговому центрі — інфраструктура й комунікації є, ти відкриваєш точку й готуєш страви. Конструктор сайтів / Heroku-подібний деплой — «кинь код, решта підніметься».

У всіх цих прикладах принцип однаковий: **інфраструктуру й середовище виконання тримає хтось інший — ти фокусуєшся на своєму застосунку**.

==PaaS== (Platform as a Service) стоїть між [[IaaS]] і [[SaaS]]. [[Cloud Provider]] (або платформа поверх нього) дає:
1. Середовище виконання (runtime) — Node, Python, Java, .NET тощо
2. Інструменти деплою, масштабування, логування
3. Часто — managed БД, черги, сховище як сервіси
4. ОС і патчі під капотом (ти їх майже не чіпаєш)

Ти керуєш:
1. Кодом застосунку
2. Конфігурацією застосунку й залежностями (у межах платформи)
3. Даними й бізнес-логікою
4. Правами доступу до свого продукту

#### Що на тобі vs на провайдері
| Шар | Хто керує |
|---|---|
| Фізика, мережа DC, [[Virtualization]] | Provider |
| ОС, runtime, middleware платформи | Provider |
| Застосунок | Ти |
| Дані | Ти |

#### Типові приклади
1. Heroku, Google App Engine, Azure App Service
2. Managed Kubernetes / Cloud Run / Elastic Beanstalk (часто близькі до PaaS)
3. Managed databases як частина платформи (RDS/Cloud SQL у зв'язці з деплоєм)

#### Коли обирають PaaS
1. Швидкий старт продукту без адміністрування серверів
2. Стандартний стек, який платформа вже вміє
3. Команда хоче писати фічі, а не патчити ОС

#### Trade-off
Менше контролю, ніж у [[IaaS]]: складніше «нестандартне» під капотом, можливий vendor lock-in.

*PaaS = оренда платформи для коду. Нижче (більше контролю) — [[IaaS]], вище (готовий продукт для юзера) — [[SaaS]].*
