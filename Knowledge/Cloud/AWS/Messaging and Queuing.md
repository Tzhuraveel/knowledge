> Спосіб комунікації між частинами системами, в якій вони не взаємодіють один з один напряму, а передають повідомлення через посерединка. Таким чином забезпечується ізольованість цих частин і якщо одна з них впаде, то це не впливає на інші і вони можуть продовжуватись функціонувати незалежно.

В сьогоденні це є важливою частиною кожного сервісу, апки, оскільки це забезпечує постійну доступність і відмостійкість системи. Якщо, наприклад, одна частина падає, то вся інші функціонує.

AWS надає декілька рішень для такого типу комунікації: [[SQS]], [[SNS]], [[EventBridge]] і [[Amazon MQ]].

#### AWS SQS

Черга, куда одні сервіси (producer) кладуть messages , а інші самі забирають їх звідти (consumer) з допомогою pooling. Кожен message обробляє лише один consumer. Підходить, коли треба **розвантажити** обробку задач і гарантувати, що кожну задачу зробить рівно один виконавець (наприклад, черга задач на обробку).

Детально: [[SQS]].

#### AWS SNS

Pub/sub-сервіс: producer публікує message в topic, а SNS **розсилає (push)** його одразу всім підписникам. На відміну від SQS, тут один message може отримати багато отримувачів. Підходить для сповіщень і fan-out.

Детально: [[SNS]].

#### AWS EventBridge

Event bus для маршрутизації подій між сервісами за правилами (rules). Вміє фільтрувати й направляти події до багатьох цілей, інтегрується з купою AWS-сервісів та SaaS. Підходить для event-driven архітектур.

Детально: [[EventBridge]].

#### Amazon MQ

Керований брокер повідомлень на базі стандартних движків (ActiveMQ, RabbitMQ) з підтримкою звичних протоколів (AMQP, MQTT тощо). Підходить, коли треба **мігрувати** наявну систему на стандартному брокері в хмару без переписування.

Детально: [[Amazon MQ]].
